## 1. Problem Statement（问题陈述）

招聘环节中，**简历筛选量大、筛选标准漂移、面试反馈难以横向比较** 这三件事是普遍且高频的痛点：

- **筛选量大**：HR / 招聘 1 个岗位常常收到几百份简历，人工通读一份平均 3–5 分钟，单岗初筛就吃掉 1–2 个工作日。
- **标准漂移**：不同 HR、不同用人经理对"什么是合格"理解不一，导致同一份简历给出差距较大的评价；且判断口径会随心情、疲劳度漂移。
- **反馈难对齐**：面试官写评语自由发挥，跨候选人、跨面试官无法横向比较，HRBP 复盘时只能凭印象。

**不解决的后果**：
- 业务侧：用人经理抱怨"招不到合适的人"，实际上是被流程损耗掉了——好简历被漏看，差简历被强推。
- HR 侧：HR 沦为"搬运工"，价值感低、流失率高。
- 公司侧：招聘周期拉长 → 业务空转；质量失控 → 二次招聘成本。

**本产品要解决的核心问题**：在岗位标准下，**批量、可解释地完成初筛与排序**，并自动输出可复用的**结构化面试追问问题库**，让 HR 和用人经理从"凭感觉"切换到"凭证据"。

**已知输入**：
- 一份岗位标准（JD + 硬性门槛 + 能力权重）
- N 份简历（PDF / DOCX / TXT）

**期望输出**：
- 候选人排序榜（带可展开证据）
- 每位候选人的风险点
- 配套的结构化面试追问问题库

## 2. Goals（产品目标）

遵循"结果而非产出"原则，目标可衡量：

| # | 目标 | 类型 | 衡量方式 | 目标值（v0.1 Demo 锚定） |
|---|------|------|----------|--------------------------|
| G1 | 单岗位初筛耗时下降 | 用户价值 | "上传到出榜"端到端时间 | < 60 秒（20 份简历以内） |
| G2 | 跨面试官反馈口径一致性 | 用户价值 | 同岗 N 位面试官评分的离散度（标准差 / 极差） | 较基线下降 30% |
| G3 | 招聘周期缩短 | 业务价值 | 投递 → Offer 平均天数 | 较基线下降 20% |
| G4 | 演示可闭环、零成本上手 | 业务价值 | 新用户从"零环境"到"出榜"所需步骤 | ≤ 3 步（含加载样例数据） |
| G5 | 关键判断**可解释、可复盘** | 业务价值 | 每条匹配结论是否能展开看到证据 | 100% 可展开（无黑盒总分） |

> **G1/G2/G3 在 Demo 阶段难以严格量化**，本阶段以 G4/G5 作为可验收目标，G1–G3 作为 v1 上线后 30/60/90 天的回访目标。

## 3. Non-Goals（非目标 / 显式不做）

为防止范围蔓延，下列项本期明确**不做**：

| 不做项 | 原因 |
|--------|------|
| **ATS / 招聘系统对接**（如对接 Moka、北森等） | 涉及账号、计费、合同，本期 Demo 阶段投入产出比低；v2 视客户需求启动 |
| **视频面试 / 录音分析** | 单独的产品线，合规与算法复杂度高 |
| **完整权限体系与多租户** | Demo 阶段假定"内部使用、单租户"；RBAC 留到 v1.0 |
| **大规模向量库 RAG 检索** | 当前是"小批量 + 强规则"，向量检索在候选集 > 1k 时才显价值 |
| **自动背调 / 学历验证** | 涉及第三方接口与合规风险，单独规划 |
| **AI 自主终面决策 / 淘汰** | 产品伦理与合规边界；系统只做"辅助判断"，不替代 HR/用人经理决策 |
| **多语种简历混合处理** | v1 只覆盖中文 + 常见英文项目名词；其它语种走"待人工"标记 |

## 4. User Stories（用户故事）

按优先级倒序排列，每条遵循 `作为 [角色]，我希望 [能力]，以便 [价值]` 格式。

### 招聘（Recruiter）—— 主力用户
- **US-1（P0）**：作为招聘，我希望**批量上传多份简历并立即得到初筛排序榜**，以便把初筛时间从 1–2 天压到几分钟。
- **US-2（P0）**：作为招聘，我希望**在排序榜上看到每位候选人的"为什么是这个分"**，以便向用人经理解释为什么推 / 不推。
- **US-3（P0）**：作为招聘，我希望**给不同岗位配不同的能力权重**，以便让权重反映这个岗位真正看重什么（如算法岗偏算法，工程岗偏稳定性）。
- **US-4（P1）**：作为招聘，我希望**对比两位候选人的证据差异**，以便在"都差不多"时快速做二选一。
- **US-5（P1）**：作为招聘，我希望**把某位候选人的面试包导出为 Markdown / PDF**，以便直接发到面试官邮箱。

### HRBP
- **US-6（P0）**：作为 HRBP，我希望**统一团队的筛选口径（硬性门槛 + 能力维度）**，以便不同招聘在同一岗位下产出可比的结果。
- **US-7（P0）**：作为 HRBP，我希望**复盘一份"被筛掉"的候选人时能看到完整证据链**，以便回应业务部门"为什么这个人没过"的质疑。
- **US-8（P2）**：作为 HRBP，我希望**看到本周期所有岗位的漏斗数据**（投递 → 初筛 → 面试 → Offer），以便做季度招聘复盘。

### 用人经理（Hiring Manager）
- **US-9（P0）**：作为用人经理，我希望**在面试前拿到针对该候选人的追问问题库**，以便把时间花在"验证风险点"而不是"想问题"。
- **US-10（P1）**：作为用人经理，我希望**能在面试中实时记录评分与备注**，以便结构化反馈直接回流到 ATS。
- **US-11（P2）**：作为用人经理，我希望**按我自己的偏好微调能力权重**（在 HRBP 设定的基础上），以便体现我对这个岗位的偏好。

### 边界 / 异常场景
- **US-12（P0）**：作为招聘，当**简历解析失败**时，系统应**明确告知哪份、哪部分失败**，以便我手动补全而不是被静默"零分"。
- **US-13（P0）**：作为招聘，当**某位候选人不满足硬性门槛**时，系统应**保留可见但降权并标注**，而不是直接隐藏。
- **US-14（P1）**：作为 HRBP，当**LLM 服务不可用**时，系统应**自动降级到 Mock/规则模式**并明确提示，以保证演示和试用不中断。

## 5. Requirements（需求规格）

按 **MoSCoW** + **P0/P1/P2** 双标签组织。每条需求配验收标准（Given/When/Then）。

### 5.1 P0 — Must Have（不交付就失去产品价值）

#### R1. 岗位标准配置
**描述**：HR/招聘 可为每个岗位定义硬性门槛与能力维度权重。
**验收标准**：
- Given HR 打开某岗位
- When TA 输入或修改硬性门槛（学历 / 工作年限 / 必会技能）和能力维度（≥ 3 个，含权重，权重和为 100）
- Then 系统校验通过后保存，下次匹配自动使用最新版本
- 校验失败时，明确指出哪个字段不合法（不静默存盘）

#### R2. 批量简历上传与解析
**描述**：支持 PDF / DOCX / TXT，单次 ≥ 20 份；解析失败可被感知。
**验收标准**：
- Given 招聘在岗位页上传 N 份简历
- When 提交后
- Then 每份简历显示"上传中 / 解析中 / 已结构化 / 解析失败"四态之一
- 解析失败时显示原因（如"PDF 加密"），允许下载原文排查

#### R3. 可解释匹配排序
**描述**：总分 = 硬性门槛通过情况 + Σ（维度分 × 维度权重）。能力维度集合中**「项目影响力」为标准独立维度**，其证据来源于简历中的项目描述（项目规模、承担角色、量化成果），而非技能关键词命中。
**未过门槛处理（Q1 决议）**：未通过硬性门槛的候选人**保留在排序榜中可见，但综合分降权并显式标记「未过门槛」**，同时列出缺口——既不静默淘汰，也不与达标候选人混淆视听。
**验收标准**：
- Given 岗位标准 + N 份候选人
- When 触发匹配
- Then 返回排序榜，每位候选人含：总分、未过门槛标记（含降权说明）、各维度分与权重（含「项目影响力」维度）、证据原文摘录、缺口说明
- 未过门槛者排在达标者之后，并带「未过门槛」徽标；可一键筛选「仅看未过门槛」复盘漏网之鱼
- **禁止**：只返回总分而无法展开证据

#### R4. 风险点与结构化追问问题库
**描述**：基于候选人的缺口、履历跳跃、频繁跳槽等信号生成风险点，并据此生成面试追问。
**验收标准**：
- Given 一位候选人的 MatchReport
- When 打开候选人详情
- Then 风险点按类别分组（履历 / 技能 / 软性），每类 ≥ 1 条追问
- 追问问题与对应风险点显式关联（可点击跳转）

#### R5. 隐私脱敏与可见范围控制（Q8 决议，P0 合规）
**描述**：候选人简历中的手机号、邮箱、身份证号等个人敏感字段在 UI 上**默认打码**；仅 HRBP 角色可显式展开查看明文，展开行为记入操作日志。
**验收标准**：
- Given 任意用户打开候选人详情
- When 页面渲染简历内容
- Then 手机号 / 邮箱 / 身份证号默认显示为 `138****1234` / `z***@example.com` 形式
- Given HRBP 角色用户
- When 点击「显示明文」
- Then 展开明文并记录一次「脱敏展开」操作日志（含候选人 ID、操作人、时间）
- 非 HRBP 角色无「显示明文」入口

### 5.2 P1 — Should Have（核心体验的强化）

#### R6. 候选人对比视图
**描述**：双人并排对比维度分、证据、风险点。

#### R7. 面试包导出
**描述**：候选人详情页 → 一键导出 Markdown / PDF（含开场、追问、收尾提示）。

#### R8. 异步任务进度
**描述**：解析 / 匹配走异步队列，前端可看到进度条；支持单份重跑。

#### R9. LLM 模式切换 UI
**描述**：页眉可显式切换 `auto / openai / mock`，并显示当前 provider 与模型名。

#### R10. 数据持久化
**描述**：岗位、候选人、匹配结果在重启后仍可见（H2 文件模式可切 PostgreSQL）。

### 5.3 P2 — Future（架构保险，不本期实现）

- **R11**. 候选人漏斗统计与可视化（对接 R9）
- **R12**. 用人经理维度微调（对接 US-11）
- **R13**. RBAC 权限（HRBP / 招聘 / 用人经理 / 候选人的可见范围）
- **R14**. 评分模型自学习（基于 Offer 后表现反哺权重）
- **R15**. ATS 对接（Moka / 北森 / 招聘官网）

### 5.4 关键设计原则（贯穿所有需求）

| 原则 | 体现 |
|------|------|
| **Why > What** | 任何总分背后必须能展开到维度分 → 证据原文 |
| **可降级** | LLM 不可用时 Mock/规则兜底，演示不中断 |
| **本地优先** | Demo 阶段全部数据在本地处理，零外部依赖 |
| **隐私默认安全** | Demo 仅用脱敏样例；UI 上对手机号 / 邮箱 / 身份证默认打码，HRBP 可展开（见 R5） |

## 6. Success Metrics（成功指标体系）

### 6.1 北极星指标

> **「单岗从简历上传到出榜」的端到端耗时中位数**（单位：秒）
> 
> 这一个数字同时承载"效率提升"+"系统稳定"+"易用"三重价值，是 Demo 和生产期共同看的核心。

### 6.2 驱动指标（按目标拆分）

| 驱动指标 | 对应目标 | 基线（v0.1 Demo 启动时测） | 目标（30 天） |
|----------|----------|----------------------------|---------------|
| 解析成功率 | G1 / G4 | 当前样例 100% | ≥ 95%（含真实 PDF） |
| 排序榜生成 P50 耗时 | G1 | 当前 ≤ 30s | ≤ 60s（20 份简历） |
| 证据可展开率 | G5 | 100% | 100%（不达标即为 P0 Bug） |
| 面试包生成成功率 | G1 | 100% | ≥ 99% |
| Mock 模式可用率 | G4 | 100% | 100%（无 Key 必可演示） |

### 6.3 健康指标（防止"快但坏"）

| 健康指标 | 告警阈值 | 说明 |
|----------|----------|------|
| LLM 调用失败率 | > 5% | 触发 Mock 降级并提示 |
| 简历解析失败率 | > 10% | 解析器可能升级或回退 |
| 前端主流程崩溃率 | > 1% | 影响 G4 演示目标 |
| 证据字段缺失率 | > 0% | 违反 G5，**必须为 0** |
| 单份简历平均大小 | > 10MB | 触发优化提示 |

### 6.4 回访机制

- **Demo 阶段**：每周 1 次内部试用复盘，收集 5 位真实招聘/HRBP 用户的体验反馈。
- **v1 上线后**：30 / 60 / 90 天分别做一次定量回访，目标值见 G1–G3。

## 8. Timeline & Milestones（时间线与里程碑）

> 当前仓库已覆盖 M1–M4 的可演示闭环（Mock 默认可用）。下列为**v1.0 升级**的里程碑建议。

| 阶段 | 周期（建议） | 交付物 | 验收 |
|------|--------------|--------|------|
| M1 骨架 | 1–2 天 | Monorepo、上传、H2、Mock 通链路 | 一键 Seed 出榜 |

| M3 面试包 | 2 天 | 风险点、追问问题库、详情页 | R4 验收通过 |
| M4 演示打磨 | 2 天 | Seed、空态/失败态、README | G4 验收通过 |

| M6 内测灰度 | 2 周 | 接入 1 个业务团队真实岗位 | G1/G2/G3 收集基线 |

## 9. 技术约束与架构摘要（继承自现有实现）

> 此节是上一版 PRD 的工程化骨架，**作为产品决策的硬约束保留**，变更需走 RFC。

### 9.1 技术栈

| 层 | 选型 |
|----|------|
| 前端 | React + Vite + TypeScript + Ant Design |
| 后端 | Java 17 + Spring Boot 3 + Maven |
| 数据库 | H2（文件模式，可切 PostgreSQL） |
| 简历解析 | Apache PDFBox + Apache POI |
| LLM | OpenAI 兼容网关（可接 DeepSeek 等）+ Mock 双模式 |
| 仓库路径 | `~/IdeaProjects/hr-resume-match` |

### 9.2 LLM 模式

- `LLM_MODE=auto`：有 API Key 走真实模型，否则 Mock
- 支持 `OPENAI_API_KEY` / `OPENAI_BASE_URL` / `OPENAI_MODEL`
- 兼容旧变量：`DEEPSEEK_API_KEY` / `DEEPSEEK_BASE_URL` / `DEEPSEEK_MODEL`

### 9.3 系统架构

| 层 | 组件 | 职责 |
|----|------|------|
| Web | Vite React App | 岗位、上传、榜单、详情、面试包 |

## 10. 风险与对策

| 风险 | 影响 | 对策 | 责任人 |
|------|------|------|--------|
| 简历解析质量波动 | 字段缺失、证据链断裂 | 解析状态可见；样例用纯文本兜底；提供"重跑解析" | 工程 |
| LLM 不稳定 / 无 Key | 演示翻车 | Mock 模式 + JSON 校验 + 自动降级 + UI 显式提示 | 工程 + 产品 |
| 「可解释」变黑盒 | 业务不信任 | 强制证据字段，证据缺失率告警必须为 0；门槛可视化 | 产品 |
| 隐私合规 | 不可使用真实简历 | Demo 仅脱敏样例；UI 自动打码手机/邮箱 | 法务 + 产品 |
| 评分"看似客观"导致 HR 放弃判断 | 招聘质量反而下降 | 文案明确"辅助而非替代"；高亮风险点需面试官复核 | 产品 |
| P2 范围蔓延 | 排期失控 | MoSCoW 评审节奏：每两周一次；新增需求必砍一项 | PM |
| **LLM 凭证泄露** | Key 被盗刷、产生非预期费用、数据外泄 | ① Key 只存 `.env`（已 gitignore），代码零硬编码；② `.env.example` 仅占位符；③ Key 定期轮换（≤ 90 天）；④ 泄露应急：立即在网关后台禁用 → 生成新 Key → 更新 `.env` → 全局搜索确认无残留 | 工程 + 安全 |

## 12. Glossary（术语表）

- **硬性门槛（Hard Gate）**：不满足即降权或淘汰的条件，如学历、工作年限、必会技能。
- **能力维度（Dimension）**：用于评价候选人的能力切面，如"系统设计 / 工程实现 / 沟通协作"。
- **能力证据（Evidence）**：简历中支持或反驳某项能力评分的原文摘录。
- **风险点（Risk Flag）**：从简历中识别出的可能影响面试判断的信号，如频繁跳槽、技能断层。
- **追问问题库（Interview Pack）**：与风险点绑定的结构化面试问题集合。
- **可解释匹配（Explainable Match）**：总分可逐层拆解到维度分、证据原文、缺口说明的匹配结果。
- **降权展示（Demote but Visible）**：未过门槛仍可见，但综合分被下调并显式标记。
